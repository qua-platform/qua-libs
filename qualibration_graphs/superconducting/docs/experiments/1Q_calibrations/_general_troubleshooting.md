# General Troubleshooting &amp; Parameter Tuning Heuristics

Every node doc's own `## Troubleshooting` and `## Parameter Tuning Heuristics` sections link back to this page for issues that recur across many different nodes in this library, so they aren't repeated dozens of times with slightly different wording. Each node's own doc covers what's genuinely specific to it — its own physics, its own parameter names, its own known bugs. This page is the general-purpose complement, not a replacement: where a node's own doc adds nuance to one of the items below (a specific parameter to adjust, a specific mechanism), that node-specific version takes precedence.

## General Troubleshooting

1. **A node reports "successful" for a qubit, but the plotted result clearly looks wrong, noisy, or implausible.** → Several nodes in this library have success/outcome checks that are structurally weak, hardcoded, or effectively vacuous — a check that only rejects `NaN`, or a comparison that's almost always true by construction. Some of these are called out explicitly in individual docs, but treat this as a general rule for the whole library: **always visually inspect the plotted fit before trusting a "successful"/"failed" label**, especially on a node you haven't used before or after a source update.
2. **A node behaves inconsistently, or only misbehaves, when run with `multiplexed=True`, but is clean when the same qubit is run alone (`multiplexed=False`).** → Concurrent pulses on other qubits' drive, flux, or readout lines during multiplexed execution can crosstalk into the qubit you're measuring. Re-run the suspect qubit alone to confirm; if the discrepancy disappears, treat it as a crosstalk characterization/compensation issue elsewhere in the system, not a bug in the node you're running.
3. **Setting `reset_type="active"` or `"active_gef"` doesn't obviously break anything, but doesn't seem to help either, or subtly degrades results.** → Active reset is only as good as its own calibration. If the active-reset method hasn't itself been calibrated and verified recently (or has drifted), selecting it here degrades reset fidelity *silently* rather than raising an error. Fall back to `reset_type="thermal"` to isolate whether the reset method itself is the problem before debugging anything else.
4. **A long-running node (many random sequences, many averages, a large sweep) hangs or throws an unexpected error partway through analysis, with no clean per-qubit `"failed"` outcome.** → Some of this library's shared curve-fitting helpers (`qualibration_libs.analysis`) open a diagnostic `plt.show()` window inside their failure-handling path when a fit doesn't converge, before returning a null result. In a headless/non-interactive/automated run this can hang rather than fail gracefully. Treat a hang shortly after data collection finishes as a likely fit-convergence issue for at least one qubit, not a hardware or infrastructure problem.
5. **Re-analyzing a historical run via `load_data_id` gives a different result than the original run reported.** → `load_data_id` replays the *data* from a past run, but any analysis step that reads the qubit's *current* configured state (e.g. using the current `RF_frequency` to convert a swept detuning into an absolute frequency) reads it as of *now*, not as of the original run. If the qubit's state has changed since then, re-analysis and the original run can legitimately disagree.
6. **A node appears to do nothing, or produces an empty/trivial result.** → Check the common `simulate` and `load_data_id` parameters first — both bypass real hardware execution entirely (simulation, or historical-data re-analysis), and it's easy to leave one set from a previous debugging session.

## General Parameter Tuning Heuristics

1. **Result is noisy, has large run-to-run scatter, or a fit barely converges.** → Increase the node's averaging parameter (usually `num_shots`, or for randomized-benchmarking-style nodes, `num_random_sequences`) first — it's the cheapest, most universal lever for statistical noise, though it does nothing for a systematic bias or a genuine miscalibration.
2. **A feature of interest (a peak, a resonance, a threshold) doesn't appear anywhere in the swept range.** → Before reaching for more drive power or more averages, check whether the true value simply sits outside the current sweep window — widen the relevant span/range first. It's a cheaper and more common fix than it looks.
3. **A spectroscopic or Rabi-type feature is either invisible or washed out/broadened beyond recognition.** → This is nearly always a drive-amplitude problem, and it cuts both ways: too weak a drive means too little population moves at all (no visible feature); too strong a drive broadens or shifts the feature until it disappears into the noise floor (power broadening). If a peak is missing, try raising the amplitude *and* lowering it before assuming a hardware problem — there's rarely a way to predict the right value ahead of time, since how strongly a given qubit couples to its drive line is often exactly the unknown a first pass is trying to characterize.
4. **You need higher confidence in a result, but aren't sure whether to spend run-time budget on more averages or finer sweep resolution.** → These trade off differently: more averages (`num_shots`) reduce statistical noise on a value you're already sampling adequately; more sweep points improve the *resolution* of a feature you're not yet sampling finely enough to resolve. If the fit looks smooth but the reported value bounces between re-runs, add averages. If the fit itself looks jagged or undersampled around the feature, add sweep points instead.
5. **The true value being searched for is very uncertain in magnitude** (an unfamiliar qubit, a fresh bring-up, a large suspected drift). → A coarse-then-fine, two-pass strategy is usually more efficient than a single fine sweep: run once with a wide-but-coarse window to locate the feature roughly, then re-run centered on that rough location with a narrower, finer window. Several nodes in this library apply this idea to a specific parameter (e.g. Ramsey's detuning-vs-bandwidth tradeoff); the same shape of strategy generalizes to most sweep-based nodes when starting from a poor prior.
